# Soft-block: инструкции и команды исполнителю

Основной документ — [soft-block-captcha-plan.md](soft-block-captcha-plan.md). Он является единственной спецификацией архитектуры. Этот файл — вспомогательные задания и команды. При полном запуске агент выполняет их последовательно без запроса подтверждения после каждого шага. Если пользователь явно просит один этап, выполняется только он.

## 1. Общий промпт — вставлять перед каждым заданием

```text
Работаем в /www/antiddos. Общаемся по-русски, кратко и конкретно.
Прочитай AGENTS.md, если он есть, и docs/soft-block-captcha-plan.md целиком.
Это спецификация будущей реализации, а не описание уже существующих возможностей.

При поручении «выполни весь план» последовательно выполни A–I и финальное review. При поручении отдельного шага выполни только указанный шаг. Сначала проверь состояние git, предыдущий
progress.md и существующий код. Сохрани пользовательские изменения. Не меняй
работающие systemd-службы, /etc/nginx, /etc/antiddos, firewall или bgt.my.
Используй изолированные временные конфиги, логи, БД, сокеты и localhost-порты.
Не запускай scripts/soak-test.sh: он предназначен для другого сценария.

Перед изменениями кратко назови результат, который должен получиться.
Реализуй минимально достаточное решение. Не заменяй auth_request на Lua,
reverse proxy или внешний CAPTCHA API. После закрытия критериев шага переходи к следующему, если поручен весь план.
Не подменяй реальный Nginx моками в тестах его поведения.

Запусти проверки, соответствующие изменению. Сохрани команды, exit codes,
версии и результаты в runtime/softblock/<run-id>/progress.md.
Не называй пропущенный тест успешным. Missing dependency и ошибка реализации
должны быть явно различены. Не скрывай ошибки через || true.

При провале gate останови зависимые работы и исправляй этот gate.
Исправляй реализации в рамках зафиксированной архитектуры. При доказанной
невозможности контракта сохрани воспроизводимый blocker; не заменяй архитектуру молча.
Заверши созданные тестовые процессы, сохрани артефакты. Не используй pkill -f:
завершай только процессы, созданные своим harness и зарегистрированные им.
Не коммить, не пушь, не делай релиз без отдельного указания.

После каждого этапа обнови progress.md и продолжи следующий при полном поручении.
В конце всей порученной работы: что изменил; какие проверки реально прошли; какие ограничения остались;
путь к отчёту; какой следующий шаг готов к выполнению. Пиши коротко.
```

## 2. Подготовка: существующие команды

Выполнять из корня репозитория. Эти команды не запускают нагрузку и не устанавливают сервисы:

```sh
cd /www/antiddos
git status --short
git branch --show-current
git log -1 --format='%h %s'
go version
node --version
npm --version
command -v nginx
nginx -V
```

Отсутствующий Nginx означает, что gate A пока нельзя выполнить. Установку пакета на хост не маскировать как обычную проверку; использовать подготовленную изолированную среду либо явно согласованную установку. Не выполнять автоматически `sudo nginx -T`: может вывести секреты работающего сайта.

Создание ветки реализации **после проверки состояния git**:

```sh
git switch -c feature/soft-block-captcha
```

Эта команда подходит, когда текущая ветка документа основана на нужном dev и ветки реализации ещё нет. Если ветка уже существует — проверить её и продолжить, не удалять и не пересоздавать. Если dev ушёл вперёд — сначала безопасно сохранить план и локальные изменения, затем обновить базу; не делать reset/stash с потерей контекста. Незакоммиченный план должен остаться доступен на новой ветке.

Baseline Go перед первым изменением; далее повторять по смыслу изменения:

```sh
cd /www/antiddos
go test ./...
go test -race ./...
go vet ./...
mkdir -p runtime/softblock/build
go build -o runtime/softblock/build/antiddos ./cmd/antiddos
```

Race и SQLite требуют рабочего CGO/C toolchain. Ошибку окружения записать как blocker, не удалять тесты и не переключать SQLite ради прохождения сборки.

Frontend, когда меняются GUI или встроенные assets:

```sh
cd /www/antiddos/web
npm ci
npm run build
npm run test:e2e
```

По текущему `web/playwright.config.ts` E2E использует `/usr/bin/google-chrome` или `CHROME_PATH`; порт по умолчанию 18082. `npm run test:e2e` сам поднимает harness и собирает frontend. Не запускать `node web/tests/serve.mjs` отдельно. Сборка обновляет embedded assets: просмотреть diff и включать их только с соответствующим GUI-изменением. Если порт занят чужим процессом, задать свободный `ANTIDDOS_E2E_PORT`, не убивать владельца порта.

## 3. Промпт A: сначала доказать работу Nginx

```text
В рамках этапа A выполни соответствующие проверки Nginx из основного плана.
Создай воспроизводимый integration harness с отдельным Nginx на localhost,
тестовым HTTPS, mock auth backend и upstream со счётчиком обращений.
Все файлы и PID держи в отдельном run-dir; никаких изменений хостового Nginx.

Проверь: allow 204; challenge 403; недоступный/медленный backend; собственные
401/403/429/500 upstream; GET/HEAD/POST; proxy_pass и FastCGI при доступном
тестовом backend; internal rewrite; чужие клиентские metadata-заголовки.
Докажи сохранение исходного метода/URI и отсутствие обхода существующей авторизации.
Проверь выдачу заглушки и log-маркер application/challenge/service из раздела «Логи и защита от повторного обнаружения заглушки».
Не считай произвольный ответ 429 приложения нашей заглушкой.

Результат: fixtures и исполняемый тестовый runner, отчёт с фактическими ответами
и счётчиками upstream. Создай tests/integration/softblock/run.sh с командой
--scenario nginx-contract --output <run-dir>. Runner обязан чистить свои процессы
при success/failure/SIGINT. Если FastCGI ещё не проверен, отметь это как незакрытый
gate, а не как поддерживаемый сценарий. Основной daemon пока не меняй.
```

## 4. Промпт B: конфигурация и события логов

```text
Выполни шаг B после успешного A. Прочитай отчёт A и используй подтверждённый
шаблон логирования. Добавь новый режим, sites/hosts/source mapping и optional
признак происхождения ответа в request.Event/Parser.

Старые конфиги/combined и режимы должны проходить прежние тесты.
Для soft-mode валидируй явную связь source->site, уникальные hosts, пригодный
HTTP log format и поддержку маркера. Не обещай автоматически определить,
какие домены реально пишутся в произвольный combined log.
Учти служебные маршруты: общая статистика учитывает их, Engine не создаёт
нарушения от нашей проверки. Ответ приложения с таким же HTTP-статусом
по-прежнему анализируется. Сохрани новые поля при редактировании через ConfigService.

Добавь тесты корректных/некорректных связей, legacy-конфига и round-trip GUI save.
Обнови пример в плане и fixtures по реально принятой схеме. Не подключай пока
режим к реальным действиям launcher: неизвестный/неподключённый режим должен
явно завершаться ошибкой, а не попадать в nftables по ветке else.
```

## 5. Промпт C: решения, SQLite и восстановление

```text
Выполни шаг C. Реализуй softblock Manager и таблицу soft_block_decisions.
Используй key(site,rule,IP), проверку blockpolicy, clock injection и строгий порядок
commit->map->revision. Не меняй семантику существующего firewall Manager.

Проверь: повтор не продлевает; два правила независимы; whitelist одного правила
не отменяет другое; global whitelist отменяет оба; expiry разрешает без cleanup;
restart сохраняет исходный deadline; ошибка SQL не публикует успех; удалённые
правила/сайты не восстанавливаются; выключение режима отменяет прежние решения.
Учитывай ограничение ёмкости и атомарность отмены. Протестируй миграцию старой БД.

Результат: unit + SQLite integration tests, go test/race для затронутых пакетов,
короткий отчёт. Сервис проверки и Nginx пока не запускай для реального сайта.
```

## 6. Промпт D: feed и быстрый check

```text
Выполни шаг D. Реализуй отдельный read-only Unix feed, versioned snapshot,
heartbeat и challenge-клиент. Контракт берётся из раздела «Feed и состояния доступности».
Снимок полностью валидируется до атомарной замены; unchanged не освежает
связь при неверных epoch/revision. На HTTP request path нет SQLite или RPC к daemon.

Проверь два сайта, пустой/старый/обрезанный snapshot, смену epoch, неверные IP,
превышение размера, expiry, disabled, starting, stale и recovery.
Добавь тесты отсутствия гонок и benchmark lookup с 1/10000/50000 leases.
Benchmark измеряет результат, не содержит произвольного pass по таймингу CI.
Раздели публичный check mux и будущую административную поверхность.
```

## 7. Промпт E: реальная локальная проверка и cookie

```text
Выполни шаг E и gate провайдера. Выбери совместимые зафиксированные версии ALTCHA widget
и Go library, проверь лицензии и локальную раздачу всех assets без внешней сети.
Реализуй provider, одноразовое server-side задание, привязку к browser session,
CSRF/Origin, безопасный return URL и подписанную cookie по разделам «Проверка браузера и cookie» и «Лимиты ресурсов».

Не принимай алгоритм/cost/memory/parallelism из пользовательского payload:
сопоставляй его с сохранённой задачей до дорогой проверки.
Добавь лимиты памяти, in-flight и числа limiter-ключей. Семафор не создаёт
неограниченную очередь. Не выдавай cookie на тестовую кнопку в production.

Проверь неверные/поддельные/повторные и параллельные verify, чужой host/site,
слишком большие payload, expiry, rotation, restart, потерю ответа после verify,
cookie в реальном HTTPS-браузере. При потере успешного ответа допустима новая
проверка; повтор одноразового задания не выдаёт новую cookie.
Сохрани измерения CPU/RAM verify и времени решения на слабом клиенте.
```

## 8. Промпт F–G: запуск и установка

```text
Выполни F, затем G, после прохождения C/D/E. Подключи компоненты в app/CLI,
добавь отдельный challenge unit, sockets/groups и передачу рабочих настроек через feed.
Никакого автоматического чтения админской БД или вызова nft из challenge.
Launcher выбирает режим явным switch; soft-mode не получает CAP_NET_ADMIN.

Добавь optional --soft-block в installer и генератор snippets с preview по умолчанию.
Не переписывай чужие server/location/log_format. Установщик сохраняет конфиг
и ключи при повторном запуске. Выводит include, проверку, reload и rollback.
TTL/sites передаются из основного конфига через feed после рестарта daemon.
Ключи доступны через systemd credentials; после ротации рестартуй только тестовый challenge.

Проверь установку/права/повторную установку/отключение на disposable окружении.
Переключение из nftables проверяй в изолированном network namespace/VM;
никогда не очищай firewall хоста. Если окружение недоступно — явно blocked.
```

## 9. Промпт H: GUI и monitor

```text
Выполни H. Встрой soft-mode и статистику проверки в существующий monitor/GUI.
Сохрани admin/viewer авторизацию. Показывай site/source/rule/expiry, running и saved
режимы, необходимость рестарта конкретных units, stale/degraded и fail-open.
Не называй проверку firewall-блокировкой. Bytes остаются размером ответа Nginx.

У административных endpoint отдельный socket; публичный Nginx не имеет к ним
доступа. Не предоставляй GUI произвольную запись Nginx-конфига/команд systemd.
При недоступной статистике challenge основной dashboard остаётся доступен.
Пройди frontend build, browser E2E и проверки прав admin/viewer.
```

## 10. Промпт I: итоговые проверки и soak

```text
Выполни I после прохождения A–H. Пройди матрицу раздела «Матрица обязательных проверок» на изолированном
HTTPS Nginx. Используй реальные Engine/Manager/provider и отдельные логи/SQLite.
Сравни baseline Nginx, allow, cookie, challenge и outage. Укажи фактические RPS,
concurrency и p50/p95/p99; метрики CPU/RSS/heap/goroutines/FD снимай раз в секунду.

Добавь в integration runner сценарий full и отдельный soak runner с параметрами
--duration, --seed, --output и явным локальным target. Seed делает всплески
воспроизводимыми. Перед стартом проверь, что target и PIDs принадлежат fixture.
Сначала 40 минут; при успехе 6 часов. Не запускай нагрузку на bgt.my и не используй
существующий production soak script. Не утверждай отсутствие утечки только по RSS.
Все дочерние процессы завершаются при SIGTERM и после теста.

Актуализируй README только реально проверенными командами. Подготовь отчёт и diff
для пользователя. Не публикуй релиз и не делай commit/push автоматически.
```

## 11. Команды будущего integration runner

**Эти runner ещё нужно создать на шагах A и I. Сейчас команды ниже не работают.** Агент должен реализовать указанный CLI, чтобы следующий исполнитель использовал одинаковый способ запуска:

```sh
cd /www/antiddos
bash tests/integration/softblock/run.sh --scenario nginx-contract --output runtime/softblock/nginx-contract
bash tests/integration/softblock/run.sh --scenario full --output runtime/softblock/full
bash tests/integration/softblock/soak.sh --duration 2400 --seed 20261020 --output runtime/softblock/soak-40m
bash tests/integration/softblock/soak.sh --duration 21600 --seed 20261020 --output runtime/softblock/soak-6h
```

Runner запускает fixture сам, выделяет свободные loopback-порты и отказывается от не-loopback target. Не использовать fixed production port 80/443. Повторное использование непустого output-каталога должно завершаться понятной ошибкой, а не перетирать предыдущий отчёт. Шестичасовой запуск выполняется только после оценки короткого отчёта.

## 12. Промпт независимого review

```text
Проверь реализацию текущего шага по docs/soft-block-captcha-plan.md и diff.
Сначала изучи реальные изменения, затем отчёт проверок. Не принимай слова
«всё работает» без команд и артефактов. Ищи нарушения контрактов, обход проверки,
ошибки Nginx inheritance/error_page, некорректный исходный IP/метод, race/expiry,
неограниченную память, доступ публичного socket к admin API и регрессии legacy.

Для каждого замечания укажи: файл/строку, конкретный сценарий, последствие,
минимальное исправление и тест, который поймает дефект. Разделяй найденный баг
и непроверенную гипотезу. Не делай рефакторинг ради стиля. Если критичных проблем
не нашёл, перечисли оставшиеся непроверенные gates. Сервисы хоста не трогай.
```

## 13. Шаблон progress.md для передачи другой модели

```markdown
# Soft-block: шаг <A–I>, <дата>
Base SHA:
Working branch:
Цель шага:
Статус: выполнен / частично / blocked

## Изменения
- Файл → поведение → причина.

## Проверки
| Команда | Exit code | Результат | Артефакт |
|---|---:|---|---|

## Нерешённое
- Конкретный blocker или непроверенный сценарий.
- Какие шаги зависят от него.

## Окружение и очистка
- Версии Nginx/Go/provider, порты и run-dir.
- Какие PID/unit созданы; подтверждение завершения.
- Работающие сервисы пользователя не изменялись / точное согласованное изменение.

## Передача
- Следующий шаг и его входные данные.
- Незакоммиченные изменения, которые необходимо сохранить.
```

Сам факт наличия отчёта не закрывает gate. Результат должен воспроизводиться указанной командой на описанном окружении.
